# /ci.fix - GitHub Actions Failure Analysis & Resolution

**Description**: Monitor GitHub Actions for failures, diagnose root cause, and either create an issue or fix with a PR.

**Scope**: project

---

## Command Instructions

### Invocation Modes

- `/ci.fix` - Check latest failed run, analyze, and fix/issue
- `/ci.fix check` - Just check for failures, don't act
- `/ci.fix run <run_id>` - Analyze specific workflow run
- `/ci.fix --auto-pr` - Automatically create PR for fixable issues

---

## Execution Flow

### Phase 1: Detect Failures

```bash
# Get recent failed workflow runs
gh run list --status failure --limit 5 --json databaseId,name,conclusion,headBranch,createdAt

# Get details of most recent failure
gh run view <run_id> --json jobs,conclusion,headSha,headBranch
```

**Output**: List of failed runs with metadata

### Phase 2: Download & Analyze Logs

```bash
# Download logs for failed run
gh run view <run_id> --log-failed

# Or get specific job logs
gh run view <run_id> --job <job_id> --log
```

**Parse logs for**:
1. **Test failures**: `FAILED`, `AssertionError`, `pytest` output
2. **Lint errors**: `ruff`, `eslint`, `mypy` output
3. **Build errors**: Compilation failures, missing dependencies
4. **Type errors**: TypeScript `tsc` errors
5. **Import errors**: Missing modules, circular imports

### Phase 3: Classify Failure Type

| Failure Type | Signals | Auto-Fixable? |
|--------------|---------|---------------|
| **Lint error** | `ruff check`, `eslint` output | ✅ Yes |
| **Format error** | `black`, `prettier` diff | ✅ Yes |
| **Type error** | `mypy`, `tsc` errors | ⚠️ Sometimes |
| **Test failure** | `pytest`, `jest` failures | ⚠️ Sometimes |
| **Build error** | Compilation, bundling | ❌ Usually not |
| **Dependency error** | `pip install`, `npm ci` fails | ⚠️ Sometimes |
| **Flaky test** | Same test passes/fails randomly | ❌ Needs investigation |
| **Infrastructure** | GitHub runner issues | ❌ No |

### Phase 4: Decision Tree

```
Failure detected
     │
     ├─► Is it auto-fixable?
     │      │
     │      ├─► YES: Attempt fix
     │      │      │
     │      │      ├─► Fix works? → Create PR
     │      │      └─► Fix fails? → Create Issue
     │      │
     │      └─► NO: Create Issue with analysis
     │
     └─► Multiple failures?
            │
            └─► Group related failures into single issue
```

### Phase 5A: Auto-Fix (if applicable)

**For Lint Errors**:
```bash
# Python
ruff check src/ tests/ --fix
black src/ tests/

# TypeScript
cd frontend && npm run lint -- --fix
npx prettier --write .
```

**For Simple Type Errors**:
- Missing return type → Add type annotation
- Unused import → Remove import
- Missing Optional → Add `| None`

**For Test Failures** (simple cases):
- Assertion value changed → Update expected value
- Missing fixture → Add fixture
- Import path changed → Update import

**Verification**:
```bash
# Re-run the checks locally
ruff check src/ tests/
mypy src/
pytest tests/ -x
```

### Phase 5B: Create PR (if fix works)

```bash
# Create branch
git checkout -b fix/ci-<run_id>-<type>

# Commit fix
git add -A
git commit -m "fix(ci): resolve <failure_type> from run #<run_id>

- <specific fix description>
- Auto-generated by /ci.fix agent

Fixes workflow run: <run_url>"

# Push and create PR
git push -u origin fix/ci-<run_id>-<type>

gh pr create \
  --title "fix(ci): Auto-fix <failure_type> from workflow run #<run_id>" \
  --body "$(cat <<'EOF'
## Summary

This PR auto-fixes CI failures detected in workflow run #<run_id>.

### Failure Analysis

**Workflow**: <workflow_name>
**Branch**: <branch>
**Failed Job**: <job_name>
**Failure Type**: <failure_type>

### Root Cause

<parsed failure reason>

### Fix Applied

<description of fix>

### Verification

- [ ] Local checks pass
- [ ] CI should pass with this fix

---
*Auto-generated by /ci.fix agent*
EOF
)"
```

### Phase 5C: Create Issue (if not auto-fixable)

```bash
gh issue create \
  --title "CI Failure: <failure_type> in <workflow_name>" \
  --body "$(cat <<'EOF'
```

## Failure Pattern Library

### Python/Ruff Lint Errors

**Pattern**: `error: ... \[E...\]` or `Found N errors`
**Fix**: `ruff check --fix`

### Python/Black Format Errors

**Pattern**: `would reformat`, `Oh no!`
**Fix**: `black .`

### Python/Mypy Type Errors

**Pattern**: `error: ...` with line numbers
**Fixable cases**:
- `Missing return statement` → Add return
- `Incompatible return value type` → Fix type or add cast
- `has no attribute` → Check spelling or add type ignore

### Python/Pytest Failures

**Pattern**: `FAILED tests/...::test_name`
**Analysis**:
1. Read the assertion error
2. Compare expected vs actual
3. Check if test or code is wrong

### TypeScript/ESLint Errors

**Pattern**: `error  ...  @typescript-eslint/...`
**Fix**: `npm run lint -- --fix`

### TypeScript/tsc Errors

**Pattern**: `error TS...:`
**Fixable cases**:
- Missing type annotation
- Unused variable (with noUnusedLocals)
- Missing return type

### NPM/Dependency Errors

**Pattern**: `npm ERR!`, `ERESOLVE`
**Fix**: Usually needs manual intervention (lockfile conflicts)

## Configuration

### In AGENTS.md or project config

```yaml
ci_fix:
  # Auto-create PRs without asking
  auto_pr: false
  
  # Auto-fixable failure types
  auto_fix_types:
    - lint
    - format
    - simple_type_errors
  
  # Always create issues for these
  issue_only_types:
    - test_failure
    - build_error
    - dependency_error
  
  # Labels to apply to issues
  issue_labels:
    - ci
    - bug
    - automated
  
  # Branch naming
  fix_branch_prefix: "fix/ci-"
```

## Integration Points

### Proactive Monitoring

Can be combined with a cron/webhook to:
1. Poll `gh run list --status failure` periodically
2. Auto-analyze new failures
3. Notify via Slack/Discord with analysis
4. Create issues/PRs automatically

### Post-Push Hook

After pushing code:
1. Wait for CI to complete
2. If failure, auto-analyze
3. Offer to fix or create issue

---

## Safety Guards

1. **Never force push** to main/master
2. **Always verify fix locally** before PR
3. **Require human approval** for test changes
4. **Don't auto-fix** if >5 files affected (likely bigger issue)
5. **Create issue instead of PR** if uncertain
6. **Tag PRs** as auto-generated for review attention

---

## Error Handling

| Scenario | Action |
|----------|--------|
| No failed runs | Report "All CI passing ✅" |
| Can't download logs | Create issue asking for manual review |
| Fix breaks other tests | Revert, create issue instead |
| Multiple unrelated failures | Create separate issues for each |
| Rate limited by GitHub | Wait and retry |
